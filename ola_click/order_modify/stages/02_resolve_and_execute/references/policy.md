# Order modification — Resolution policy

- Resolve references to the current order and distinguish the exact line for each change. Verify source, status and the active line IDs. The executor validates all reviewed additions before running any part of an item change. It preserves the original variant, modifiers and comment when adjusting an existing line's quantity.
- Execute explicit owner order modifications (`add_order_discount`, `remove_order_discount`, `add_order_payment`, `remove_order_payment`, `add_order_combos`, `remove_order_combo`, `apply_order_coupon`, `update_order_status`, `cancel_order`) directly under `run-stage02.cjs` using the environment's `OLACLICK_ALLOW_WRITES` and `OLACLICK_ALLOW_DESTRUCTIVE` gates—never override them to `0` or pause for confirmation unless `orientation.json` returns `NEEDS_CONFIRMATION`.
- Swaps and decreases can require a new line and removal of an old one. The shared runner previews the actual changes. The executor adds any replacement before removing its source. A failed multi-step change requires checking which actions succeeded before retrying.
- Cancellation uses the API reason code and checks existing payments. Always check `get_order` first: **never call `cancel_order` if the order already has recorded `payments`** (explain that paid orders cannot be cancelled without removing/refunding payment). Coupons require a client on the order. Status changes follow the documented API progression.
- Use a verified ID for each payment method, payment and discount. Resolve payment methods against the list for this order's service. Determine the amount from the request, or the unpaid balance for a single payment when requested. Carry distinct amounts for split payments.
- Use the [MCP order arguments and scope reference](../tools/rules.md#order-changes-and-verification). Native removal calls use the exact keys `comboId`, `paymentId` and `discountId`. A proposed payment method on an order is distinct from a payment already collected.
